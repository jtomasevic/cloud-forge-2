**Task: Signup Identity And Tenant Activation Workflow**

**Problem**

POST /v1/accounts currently creates:

- CF-Accounts account row
- default tenant row with status = provisioning

But it does not:

- create a Keycloak user
- create a usable JWT path for that new user
- trigger CF-Provisioner
- update tenant status from provisioning

Result: signup appears successful, but the user cannot log in through Keycloak, and the default tenant stays stuck forever.

**Recommended Direction**

Use Keycloak as the identity source of truth. Do not keep two independent password systems.

Signup should:

1. Validate email/password.
2. Create CF-Accounts account.
3. Create Keycloak user for the same email.
4. Set Keycloak password.
5. Store/link Keycloak subject/user ID on the account, or store CF account ID as a Keycloak user attribute.
6. Ensure Keycloak JWT includes cf_account_id.
7. Create default tenant as active unless we also provision infrastructure during signup.

**Scope**

- Add Keycloak admin client/config to CF-Accounts:
    - KEYCLOAK_ADMIN_URL
    - KEYCLOAK_REALM
    - KEYCLOAK_ADMIN_CLIENT_ID
    - KEYCLOAK_ADMIN_CLIENT_SECRET or dev admin credentials
- Update dev Keycloak realm config so CF-Accounts can create users.
- Add repository/schema support if needed:
    - accounts.identity_provider
    - accounts.identity_subject
- Update signup service flow:
    - create account
    - create Keycloak user
    - set password
    - set cf_account_id attribute
    - create default tenant as active
- Update Keycloak realm export with protocol mapper for cf_account_id.
- Update CF-Router JWT resolution to require/use cf_account_id from token; only fall back to sub if explicitly intended.
- Add rollback/compensation behavior:
    - if Keycloak creation fails after account insert, mark account failed/deleted or delete the partial account in dev
    - return clear 5xx/409 errors

**Out Of Scope**

- Full email verification.
- Invite-only signup.
- Automatic vCluster/network provisioning during signup.
- Production-grade CAPTCHA/rate limiting, though note it as required later.

**Acceptance Criteria**

- POST /v1/accounts creates a CF account and Keycloak user.
- Newly signed-up user can call Keycloak token endpoint and receive JWT.
- JWT contains cf_account_id.
- That JWT works in Swagger Authorize.
- GET /v1/accounts/{id}/tenants shows default tenant as active.
- Existing seeded dev user still works.
- Tests cover Keycloak user creation success/failure and tenant status behavior.
- Dev docs explain signup/login flow end to end.
