# Task 11 — CF-Provisioner OpenAPI Spec

## Context

CF-Provisioner is the infrastructure provisioning and lifecycle engine. Its API allows the control plane (and operators) to provision and deprovision tenant private networks, subnets, and internet gateways. It communicates with the host Kubernetes cluster to create vCluster instances, apply Cilium policies, and manage Envoy Gateway HTTPRoutes.

This task writes the OpenAPI 3.0.3 specification — the complete HTTP contract — before any handler code is written.

Reference: `docs/cf-private-network.md` sections 5.2 (CF-Provisioner responsibility), 8.2 (provisioning flow), 9.2 (internet gateway flow), and 13.2 (OpenAPI-first rule).

### Operations

#### Networks (Private Network Lifecycle)

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/v1/networks` | Provision a new tenant private network (creates vCluster, allocates CIDRs, applies Cilium policies, stores kubeconfig) |
| `GET` | `/v1/networks/{networkId}` | Get provisioning status of a network |
| `DELETE` | `/v1/networks/{networkId}` | Deprovision a network (destroys vCluster, frees CIDRs, deletes kubeconfig) |

#### Gateways (Internet Gateway Lifecycle)

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/v1/networks/{networkId}/gateway` | Provision an internet gateway for a network (creates Envoy Gateway HTTPRoute + Cilium ingress policy) |
| `GET` | `/v1/networks/{networkId}/gateway` | Get gateway status |
| `DELETE` | `/v1/networks/{networkId}/gateway` | Remove the internet gateway |

#### Jobs (Async Provisioning Status)

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/v1/jobs/{jobId}` | Get the status of an async provisioning job |
| `GET` | `/v1/networks/{networkId}/jobs` | List all jobs for a network |

#### Subnets

| Method | Path | Description |
|--------|------|-------------|
| `POST` | `/v1/networks/{networkId}/subnets` | Create a subnet in a network |
| `GET` | `/v1/networks/{networkId}/subnets` | List subnets in a network |

#### CIDR (Internal management)

| Method | Path | Description |
|--------|------|-------------|
| `GET` | `/v1/cidr/allocations` | List all CIDR allocations (for debugging/ops) |

### Async provisioning pattern

`POST /v1/networks` is asynchronous. It returns `202 Accepted` immediately with a `Job` object. The caller polls `GET /v1/jobs/{jobId}` until the job reaches `succeeded` or `failed`. Document this in the operation description.

Similarly, `DELETE /v1/networks/{networkId}` is async and returns `202 Accepted`.

---

### Status codes

- `202 Accepted` for async provisioning operations (`POST /v1/networks`, `DELETE /v1/networks/{networkId}`)
- `201 Created` for synchronous creates (subnets, gateway when sync)
- `200 OK` for GETs
- `204 No Content` for sync deletes
- Standard `400`, `401`, `404`, `409`, `500`
