# Task 31 — CF App Service Gateway And Cilium Routing

## Context

`docs/cf-app-service.md` section 5.5 calls out a current limitation:

- Internet gateway routing currently creates an `HTTPRoute` to a placeholder backend service, not to a specific tenant app service.

This task replaces placeholder routing with service-specific routes and Cilium policies for CF App Services.

Reference:

- `services/cf-provisioner/internal/repository/gateway/`
- `services/cf-provisioner/internal/repository/cilium/`
- `dev/k8s/gateway/`

## Requirements

1. Extend Gateway repository models so routes can target a specific app service backend.
2. Replace placeholder backend routing for app service exposure.
3. Create route names derived from app service ID, not only network ID.
4. Support hostnames per public app service.
5. Create Cilium ingress policy scoped to:
   - target app service labels
   - declared exposed port
   - public subnet placement
6. Keep existing network-level gateway flow compatible.
7. Make public exposure idempotent.
8. Ensure route deletion and Cilium policy deletion are part of removing exposure.

## Public Swagger Requirement

The same internet gateway that exposes an app service must also expose its Swagger page.

For HTTP/REST services, create routes for:

- service traffic, for example `/`
- Swagger UI, default `/swagger/`
- OpenAPI JSON, default `/openapi.json`

The Swagger/OpenAPI routes must target the app service or a CloudForge docs adapter, depending on the implementation chosen in Task 34.

## Acceptance Criteria

- Gateway repository can create an HTTPRoute targeting a specific Kubernetes Service and port.
- Cilium repository can create ingress policy scoped to one app service.
- Existing gateway tests still pass.
- New tests verify no placeholder backend is used for app services.
- Removing exposure deletes service-specific route and policy.
