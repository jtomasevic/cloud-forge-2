# Task 17 — CF-Router OpenAPI Spec

## Context

CF-Router is the tenant-aware platform routing layer. It sits behind Envoy Gateway and is responsible for:
1. Validating inbound credentials (JWT from Keycloak or API key)
2. Resolving tenant context by calling CF-Accounts
3. Enriching the request with tenant metadata headers
4. Proxying the enriched request to the correct internal CF service

CF-Router's own HTTP API is minimal — it is primarily a proxy/middleware service. However it exposes a health endpoint and a route introspection endpoint for operators.

Reference: `docs/cf-private-network.md` sections 5.3 (CF-Router responsibility), 10.3 (request flow), and 13.2 (OpenAPI-first rule).

## Dependencies

Task 1 must be complete. Tasks 5 and 11 should be reviewed to understand the services CF-Router routes to.

### Security

CF-Router itself validates incoming credentials. Define two auth schemes:
```yaml
components:
  securitySchemes:
    BearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT
    ApiKeyAuth:
      type: apiKey
      in: header
      name: X-CF-API-Key
```

### Operations

CF-Router's own API surface is intentionally small. All proxied traffic is pass-through and is not part of CF-Router's own OpenAPI spec — that traffic belongs to the specs of the upstream services.

#### Health and readiness

| Method | Path | Description | Auth |
|--------|------|-------------|------|
| `GET` | `/health` | Liveness probe — returns 200 if the service is running | None |
| `GET` | `/ready` | Readiness probe — returns 200 if CF-Router has a working connection to CF-Accounts | None |

#### Route introspection (operator only)

| Method | Path | Description | Auth |
|--------|------|-------------|------|
| `GET` | `/internal/routes` | List registered route targets | `InternalSecret` header |
| `GET` | `/internal/tenant-context` | Resolve and return the tenant context for the provided credentials (for debugging) | `BearerAuth` or `ApiKeyAuth` |

### Proxy routing table (document, not spec)

CF-Router's routing table is configuration, not part of the OpenAPI spec. Document it in the spec description or as a separate note:

```
/v1/accounts/**  → CF-Accounts  (http://cf-accounts:8081)
/v1/tenants/**   → CF-Accounts  (http://cf-accounts:8081)
/v1/networks/**  → CF-Provisioner (http://cf-provisioner:8082) [provisioner networks]
/v1/gateways/**  → CF-Provisioner (http://cf-provisioner:8082) [provisioner gateways]
/v1/jobs/**      → CF-Provisioner (http://cf-provisioner:8082)
```

CF-Router adds the following headers to all proxied requests:
- `X-CF-Tenant-ID`: resolved tenant ID
- `X-CF-Account-ID`: resolved account ID
- `X-CF-Network-ID`: resolved network ID (if any)
- `X-CF-Region`: tenant region
- `X-CF-Internal-Secret`: internal shared secret (stripped from original request)
